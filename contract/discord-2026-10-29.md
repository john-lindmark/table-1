## 1. Identity
- A Discord user is one Table 1 account, and an account is one Discord user (`t1_private.discord_links`). The link
  is made by `/link` (a one-time token confirmed on the web, signed in with any method) or implicitly by signing in to
  Table 1 with Discord (Supabase's Discord provider; `auth.identities.provider_id` is the Discord user id).
- `t1_private.discord_user(p_discord_id)` resolves a Discord user id to an account: the explicit link first, then a
  Discord identity. Null = not linked. Every bot RPC that acts for someone calls `t1_private.discord_act`, which
  resolves the account and sets the request's JWT claims (`request.jwt.claim.sub` / `.role`, transaction-local) so
  `auth.uid()` is that account for the rest of the call. The bot's RPCs are callable by the service role only.
- Tokens: 24 random bytes, base64url, kept as sha256 hex in `t1_private.discord_link_tokens`, 10 minutes, one live
  token per Discord user (a new `/link` replaces it), single-use. Delivered as `https://table-1.site/discord/link#t=<token>`.

### The deck picture (2026-10-29)
The `/deck` post's embed image is the deck's picture (contract/deck-image-2026-10-20.md: header, the cards layout
grouped by type with count badges, the sideboard column) drawn on the server by the **`deck-image`** edge function:
`GET /functions/v1/deck-image/<share token>.png?v=<deck version>` → `image/png`, 1600 px wide (taller than 16:9 for
big decks), `Cache-Control: public, max-age=3600, s-maxage=86400`. The token is the deck's "Anyone with the link"
token, so whoever may open the link may see the picture; a closed link, a non-deck link or a bad token is a 404.
`verify_jwt` off (Discord's image proxy sends no JWT). The data comes from **`deck_image_data(p_token)`** (anyone with
the link, signed out too): `{name, format, version, updated_at, owner, lines: [{card_id, oracle_id, name, board, qty,
finish, type_line, cmc, set, image_ts}]}` without Considering. The function plans the picture (`layout.ts`: the same
`plan`/`fit` rules and numbers as the clients, checked against `testdata/deck-image/cases.json`), fetches each card's
art from Scryfall (`small` under 160 px drawn width, else `normal`; 12 at a time), writes the SVG (`svg.ts`: JetBrains
Mono, the Table 1 mark, foil sheen, a plain tile with the name when an image fails) and rasterizes it with resvg
(WASM from jsDelivr, fonts from JetBrains Mono's GitHub release, both loaded once per instance). Finished pictures are
cached in memory (the newest 8, by token and version). The bot addresses it with `DECK_IMAGE_URL` (default
`<SUPABASE_URL>/functions/v1/deck-image`) and the deck's `version`, so a changed deck gets a fresh picture past
Discord's cache. The web could reuse it as a share page's preview image.

### Wants and for trade (2026-10-29)
`/wants [card]` and `/trades [card]` post the account's wants or for-trade copies, as a list (up to 25 lines, then
"…and N more") or one card (its lines, with the card's picture as the thumbnail), each line `qty name · printing ·
finish · (condition) · price`, the footer with the count (and the for-trade value at market), and **Open on Table 1**
to the part's share link. Like `/deck`, a part with no live link asks first (buttons `t1:wants` / `t1:trades`, no id);
the confirm posts the whole list.

## 5. The card
`discord_event_card` returns, for any event posted in the server:
```
{event_id, name, format_label, set_name, cube_name, status, starts_at, venue_name, capacity, top_cut, auto_rounds,
 number_of_rounds, current_round, organizer_name, short_code, sign_up: open | full | closed,
 players: n, waitlist: n, player_names: [..by seat..], waitlist_names: [..], link: "https://table-1.site/s/<id>",
 guild_id, channel_id, message_id, results_message_id}
```
Names are the players' Table 1 display names (what the event already shows every player). The Discord embed:
title = name, description = `<format> · <set/cube>` + when (`<t:unix:F>`, so each viewer sees their own zone) +
venue, fields Players (`n/cap` and the names, "and N more" past 25), Waitlist, Rounds, Top 8, Join code; footer
"Table 1 · Sign-ups open/closed/full"; buttons **Sign up** (`t1:up:<event_id>`), **Drop** (`t1:down:<event_id>`),
**Open in Table 1** (link). The results embed lists rank, name, record `W-L-D` and points (top 8 fully, then "and N
more" with the link), a trophy line for the winner, footer "Final standings" or "Standings so far after round N".

## 6. The function (`discord-bot`)
- `POST /functions/v1/discord-bot`: headers `X-Signature-Ed25519`, `X-Signature-Timestamp`; verify over
  `timestamp + rawBody` with `DISCORD_PUBLIC_KEY`; refuse (401) a bad signature or a timestamp more than 5 minutes
  off. Type 1 PING → `{type: 1}`. Deployed with `verify_jwt` off.
- Slash commands and buttons answer in one database round trip, then finish side work (editing the card by its stored
  ids, storing the posted message id, telemetry) in `EdgeRuntime.waitUntil`. Button clicks answer with
  UPDATE_MESSAGE (the refreshed card) and an ephemeral follow-up to the clicker.
- Secrets: `DISCORD_PUBLIC_KEY`, `DISCORD_APPLICATION_ID`, `DISCORD_BOT_TOKEN`; `POSTHOG_KEY`, `POSTHOG_HOST`
  (optional, telemetry off when empty), `T1_ENVIRONMENT` (`production` default), `DISCORD_TELEMETRY_SALT`,
  `DECK_IMAGE_URL` (optional; see The deck picture).
- Commands are defined once in `discord-bot/commands.json` (also what `/help` and the web page read; the register
  tool `tools/discord/register.ts` PUTs them). Install URL:
  `https://discord.com/oauth2/authorize?client_id=<app>&scope=bot+applications.commands&permissions=18432`
  (Send Messages + Embed Links).

## 7. Web
- `/discord`: what the bot does (every command from `commands.json`, copied to `src/lib/discordCommands.json` with a
  parity test), **Add to your server** (`VITE_DISCORD_CLIENT_ID`; hidden when empty), and, signed in, the link status
  with Unlink. Account → Discord row opens it.
- `/discord/link#t=<token>`: signed out → the token is kept in `sessionStorage` and the sign-in buttons shown; signed
  in → `discord_link_confirm`, then "Linked · back to Discord". Both pages stay in the browser (not claimed by the
  apps; `testdata/universal-links/cases.json`).
- **Continue with Discord** (Supabase's Discord provider, on all three clients) is its own piece of work:
  `contract/discord-sign-in-2026-10-29.md`. Anyone who signs in that way is linked to the bot with nothing more to do
  (§1).

## 9. Errors the bot shows
PostgREST passes the RPC's message, which is already a sentence (`Sign-ups are closed`, `That event isn't
available`). 28000 from the bot's RPCs is "Link your Table 1 account first" and gets a **Link** button
(`t1:link`, which runs `/link`). Unknown failures: "Table 1 didn't answer. Try again." and a console error (no
personal data).
