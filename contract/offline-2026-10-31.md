# Offline and low connection (2026-10-31)

John asked whether the apps cache enough to stay useful on a bad connection. The Library side (catalog pack, collection,
decks, binders), the life tracker and rankings already did. The Play side didn't: with no signal the Events tab and any
event screen showed an error, Insights showed nothing although every pack was on the device, and the web app didn't load
at all. This contract says what every client keeps on the device and what it does when a call fails. Shared cases:
`testdata/offline/cases.json` (`OfflineTests` / `offline.test.ts` / `OfflineTest`). No server change.

## 1. Saved screens

Each client keeps, per account, the last answer to these calls as it came off the wire, with the time it was fetched:

| Saved | Key | Shown on |
| --- | --- | --- |
| `events_home` | `home` | the Events tab |
| `event_bundle` | `event-<id>` | the event screen (player or organizer) |
| events-engine `standings` | `standings-<id>` | the event screen |
| `insights_index` | `insights-index` | Insights (the packs themselves were already kept by version) |

iOS keeps them as files under Application Support/Offline/<account>/, Android under files/offline/<account>/, the web in
IndexedDB `table1-offline-<account>` (a guest's event through a claim token is keyed by the guest token's event). They
are cleared at sign-out of that account's in-memory copy only; the files stay for the next sign-in.

Rules:

- **Opening a screen shows the saved answer at once**, then asks the server. The answer replaces it and the time is
  updated.
- **When the call fails and something is saved**, the saved answer stays and the screen says
  `Couldn't refresh · last updated <ago>` as a plain (not error) notice: Events at the top of the list, the event
  screen along the bottom edge, Insights above the pickers. `<ago>` is `just now` under a minute, `N min ago` under an
  hour, `N h ago` under a day, then `N days ago` (`1 day ago`).
- **When the call fails and nothing is saved**, the error shows as before, with a **Try again** button under it.
- A cancelled call (leaving the screen) is never a failure.
- Insights: with a saved index, every pack whose version matches a file on the device loads from it with no network.

The event screen also refreshes when the app comes back to the foreground (it only did on a Realtime ping, and a
subscription that failed while offline never pinged) and the web event screen when the tab becomes visible or the
browser says it's back online.

## 2. Request timeouts

Every client's Supabase client times out: a request that gets no answer in 25 s fails (so a dead connection shows the
saved screen or the error instead of "Loading…" for a minute or more). Uploads (deck photos, avatars) get 120 s.
iOS: a URLSession with those limits on `T1Shared.client`; Android: Ktor's `HttpTimeout`; web: `AbortSignal.timeout` on the
client's `fetch` (a request with a `Blob`/`FormData` body gets the longer one).

## 3. Collection outbox

Adds already show before the server answers (contract/collection-2026-10-15.md § Shown at once). Now a batch of **adds
only** (every op has `delta > 0` and no `qty`) that fails on a **network error** is not taken back: it's kept in the
account's outbox on the device with its idempotency key, the copies stay on screen, and the batch is sent again, in
order, with the same key, before the next sync (foreground, Collection tab, after any later change). The server has
never seen it, so the same key can't make a duplicate.

- `apply` returns a result whose `batch_id` is `queued:<key>`; **Undo** on it removes the batch from the outbox and
  takes the copies back (nothing to undo on the server).
- A sync row for an item with queued adds shows the server's quantity **plus** the queued deltas (the server hasn't
  counted them yet).
- When a queued batch is refused by the server (not a network error), it's taken back and the store's error says so.
- Batches with removals or quantity sets still wait for the server and fail as before.
- The Collection home shows `N changes waiting to send` while the outbox isn't empty.
- Binder copies in queued adds show at once as before but may be hidden by a binder sync until the batch lands.

Scanning at a venue with no signal keeps every card.

## 4. Decks and cubes offline

A list made on the device is sent again each sync until the server has it (iOS since 2026-10-22, now web and Android
too: `unsaved`). And every change to a saved list (`list_edit`, `list_update`, `list_source_set`, `list_restore`,
`list_delete`) that fails on a network error is applied on the device (the apps already showed changes at once; the
web and Android apply the op locally the way the demo does) and **queued per account in order**; the queue is sent
before the next pull. A queued change the server refuses is dropped and the list re-synced from the server. A change
to a list the server doesn't have yet waits for the create, which carries the current cards.

## 5. The web app shell

`vite-plugin-pwa` (Workbox) precaches the built shell (index.html and every chunk) and takes over on the next load after
a deploy (`autoUpdate`, skip waiting, clients claim). Navigation requests fall back to index.html so every app route
opens offline; `/.well-known/*` and `/functions/*` are never served from the worker; Supabase calls aren't cached by it
(the stores above keep what the screens need). No manifest yet (no icons), so no install prompt. `_headers` serves
`sw.js` and `index.html` uncached so a new deploy is seen at once.

## 6. Telemetry

`offline_shown` (`screen`: home / event / insights, `age_s`) when a saved screen is shown because the call failed;
`outbox_queued` (`ops`) and `outbox_sent` (`batches`); `list_change_queued`.

## 7. Not done

- No outbox for removals, quantity sets, trades, wants, binder moves or rankings' saves beyond what `RankSync` keeps.
- Realtime isn't retried with backoff; a foreground or reopening the screen resubscribes.
- Images not yet seen aren't fetched ahead for offline use.
