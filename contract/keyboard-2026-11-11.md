# Keyboards go away (2026-11-11)

John: "keyboards should be dismissible in all locations. it's tough, especially on insights, when keyboard is invoked to dismiss it. even tapping on non-interactable components doesn't dismiss. then if I navigate to a screen from insights then go back, the keyboard is still up."

Before this, iOS put the keyboard away only on a tab switch, on opening or closing a panel, and when two lists were dragged; Android only after Join on an event code. A tap on a row's label, a heading, a chart or empty space did nothing; Back left the keyboard up over the screen underneath; and Add cards focused its box again on every return from a card's page.

## Rule (all three clients)

- **A tap outside the text box puts the keyboard away.** A tap in the box itself (its padding and Clear button too, since 89e2da7 made the whole box take the tap) leaves it up, and so does a tap on a control marked to keep it: the Add beside "Add a player by name", so the next name goes straight in.
  - iOS: one tap recognizer on the window (`KeyboardAway` in `UI/Kit.swift`, installed by `KeyboardAwayHost` at the root). It never cancels or delays other touches. It ignores taps in a `UITextInput` (any text box, or a web page). It waits 0.06 s, then puts the keyboard away only if the box that had it at the tap still has it, so a tap that moves to another box, or opens a screen that focuses its own box, isn't undone. `.keepsKeyboard()` marks a view; `.focusArea()` includes it. Every tap counts, buttons included (a button that opens a screen puts it away).
  - Android: `Modifier.keyboardAwayOnTap()` (`ui/components/KeyboardAway.kt`) on the activity's root, on every `T1FullScreenDialog` and on `T1Overlay` (both are their own windows). It counts only taps that nothing under them took: text boxes, buttons, rows and lists consume their own taps and drags, so Add while typing and scrolling keep the keyboard, as Android users expect. Taps on a menu's or sheet's panel (`absorbTaps`) put it away too.
  - Web, touch screens only (`lib/keyboardAway.ts`, installed in `main.tsx`): a touch that moves under 10 px blurs the focused box, unless it landed in a text box, on a `label`, or on something marked `data-keeps-keyboard`. Clicks with a mouse are left alone.
- **Dragging any list puts it away** (iOS: `.scrollDismissesKeyboard(.interactively)` set at the root, so every scroll view gets it; Insights card search keeps `.immediately`). Android and the web leave scrolling alone, as their platforms do.
- **Changing screens puts it away.** iOS: Back on any tab (`.keyboardAwayOnBack(depth)`, where a shorter path means a pop); a push is a tap, which the tap rule covers. Android: every destination change (`KeyboardAwayOnNavigate(nav)`, an `OnDestinationChangedListener`, which runs before the next screen is drawn, so a screen that focuses its box as it opens still gets the keyboard). Web: leaving a screen unmounts its box.
- **A screen focuses its box only as it first opens**, not again when you come back to it: Add cards and a deck's or cube's Edit (iOS `opened`), Add cards on Android (`rememberSaveable opened`). Insights card search already did this.

## Telemetry

`keyboard_dismissed` {how: `tap` | `navigate`}. iOS sends it only when a box gave up the keyboard; Android sends it only while the keyboard is showing; the web sends it on each blur.

## Tests

iOS `KeyboardAwayTests` (which taps count; put away after a tap; a kept tap; focus that moved isn't undone). Android `KeyboardAwayTest` (a tap on a label, in the box, on a button, a drag; screen changes). Web `keyboardAway.test.ts`. Taps can't be sent in iOS unit tests, and Robolectric hands focus back after a clear (it isn't in touch mode), so the Android tests watch for the box losing focus.
